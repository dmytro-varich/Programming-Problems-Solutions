# Test Questions

## 1. Scenario debugging

<details>

<summary> <b> Description </b> </summary>
Є chatbot-сценарій на 150-200 блоків. У логах проблемного діалогу останній шлях такий:

```bash
start → main_menu → return_flow_start → ask_order_id → check_order_action → return_router
```

Після `return_router` нових блоків немає.

Назвіть 5 конкретних речей, які перевірите першими.

Не пишіть загальний план – тільки конкретні перевірки.

</details>

### Answer

1. Насамперед перевірю pipeline та чи підключені блоки між собою для просування даних.

2. Перевірю наявні блоки, щоб переконатися, що вони дійсно обробляють ID у тому типі даних, який ми очікуємо.

3. Переконаюся, що цей клієнт дійсно є в базі даних.

4. Перевірю, чи немає помилок або опечаток у назвах змінних у pipeline, якщо обробка умов і даних здійснюється за допомогою коду.

5. Протестую та відтворю ті самі дії, які виконував клієнт, щоб зрозуміти, через що та де виникає помилка.

## 2. API debugging

<details>

<summary> <b> Description </b> </summary>

Custom action створює заявку в CRM. API повертає 422.

Payload:

```json
{

  "phone": "050 123 45 67",

  "amount": "1250,50",

  "stageId": null,


  "source": "chatbot"

} 
```

Response:

```json
{

  "error": "validation_failed",

  "fields": {

    "phone": "Invalid E.164 format",

    "amount": "Expected number",

    "stageId": "Required"

  }

}
```

Що саме зламано?

Що виправите?

Чого НЕ треба робити?

Опишіть, які логи і метрики потрібні для дебагу зазвичай

</details>

### Answer

Передані дані не пройшли бізнес-валідацію на стороні CRM.

Поле `phone` має неправильний формат, оскільки за стандартом **E.164** потрібно використовувати міжнародний формат номера телефону, тобто без пробілів, дужок і дефісів, наприклад: `+380501234567`.

Поле `amount` передано як текстовий рядок замість числа. Крім того, як десятковий роздільник використано кому (`1250,50`), тоді як API очікує число у форматі з крапкою (`1250.50`).

Поле `stageId` передано як `null`, хоча воно є обов'язковим і використовується для ідентифікації етапу (stage) в CRM.

Щоб виправити ці помилки валідації, потрібно перед відправкою запиту до CRM реалізувати логіку, яка буде автоматично приводити дані до правильного формату. Також ще до відправки запиту варто показувати користувачу повідомлення про помилки у введених даних, щоб він міг їх виправити. Це дозволить не надсилати некоректні запити до CRM і не створювати зайве навантаження на систему.

Кроки виправлення:

* **Валідація та форматування телефону.** Очистити пробіли, дужки та дефіси, додати міжнародний код країни за замовчуванням (якщо користувач його не ввів) або використати готову бібліотеку для роботи з телефонними номерами (`libphonenumber-js`, `phonenumbers`).
* **Конвертація суми.** Замінити кому на крапку та привести значення до типу `Float` / `Number` засобами мови програмування або low-code платформи.
* **Заповнення `stageId`.** Передавати валідний `stageId` замість `null`.
* **Повідомити користувача** про неправильно введені дані, щоб він міг самостійно їх виправити.

**Правильний payload:**

```json
{
  "phone": "+380501234567",
  "amount": 1250.50,
  "stageId": "stage_leads_new",
  "source": "chatbot"
}
```

**Чого не треба робити:**

* Не змінювати схему API на стороні CRM лише для того, щоб вона приймала некоректний запит.
* Не виконувати автоматичні повторні запити (retry), оскільки це помилка на стороні клієнта (4xx), і повторна відправка не вирішить проблему.

**Логи та метрики для дебагу:**

* Логи HTTP-запиту: URL, метод, заголовки, тіло запиту (без конфіденційних даних), а також повна відповідь сервера.
* Лог того, що саме користувач ввів у чаті перед тим, як бот сформував запит.
* Документація API CRM, щоб перевірити вимоги до ендпоінтів, типів даних та обов'язкових полів.
* HTTP-статуси відповідей (наприклад, 422) та частота їх виникнення.
* Кількість невдалих спроб створення лідів у CRM за певний проміжок часу.
* Час відповіді API CRM, щоб своєчасно виявляти таймаути або погіршення продуктивності сервісу.


## 3. Product agent

<details>

<summary> <b> Description </b> </summary>

Є готовий product API:

- GET /products/search

- GET /products/{id}

- GET /products/{id}/availability

Потрібен AI-агент для консультацій по товарах і замовленнях інтернет-магазину.

Опишіть MVP-рішення без зайвого overengineering:

- які MCP tools потрібні;

- що НЕ треба класти в prompt;

- коли знадобиться RAG / vector search а коли ні

- як будете текстувати, які ключові кейси маєте перевірити

</details>

### Answer

Оскільки нам уже надано готовий Product API, для MVP достатньо створити три MCP-інструменти:

* `search_products(query: string)` — мапиться на `GET /products/search`. Викликається, коли користувач шукає товар за назвою або описом (наприклад: «знайди червоні кросівки»).
* `get_product_details(product_id: int)` — мапиться на `GET /products/{id}`. Викликається, коли користувач обрав конкретний товар і хоче отримати детальну інформацію: характеристики, ціну, опис тощо.
* `check_availability(product_id: int)` — мапиться на `GET /products/{id}/availability`. Викликається для перевірки наявності товару на складі або доступності конкретних розмірів чи кольорів.

**Що не треба класти в prompt?**

* Не потрібно завантажувати всю базу товарів у системний prompt, оскільки це лише витрачатиме токени, а інформація швидко застаріватиме.
* Не варто прописувати жорсткі сценарії діалогу на кшталт: «якщо користувач сказав А —> запитай Б, якщо Б —> запитай В». Агент повинен самостійно визначати, який інструмент потрібно викликати залежно від наміру користувача.
* Для MVP достатньо короткого системного prompt, який містить: **role**, **goal**, **constraints**, **tool usage** та **error handling**.

**Коли знадобиться RAG / Vector Search, а коли ні?**

Якщо потрібна інформація вже доступна через структурований Product API, використовувати RAG немає сенсу. Пошук товарів, отримання картки товару, перевірка наявності, фільтрація за категоріями чи ціною повинні виконуватися через API, оскільки це швидше, дешевше та точніше, ніж векторний пошук.

RAG або Vector Search знадобиться тоді, коли потрібно працювати з неструктурованими текстовими даними, наприклад:

* політика повернення товарів;
* умови доставки;
* гарантійні зобов'язання;
* FAQ;
* інша документація магазину.

У цьому випадку документи можна розбити на чанки, побудувати ембеддинги та виконувати семантичний пошук.

Також Vector Search може бути корисним для складного семантичного підбору товарів. Наприклад, якщо користувач пише: «Потрібен подарунок для хлопчика 5 років, який любить динозаврів і малювання». У такому випадку звичайний пошук за ключовими словами може не знайти потрібні товари, тоді як векторний пошук по описах товарів допоможе підібрати найбільш релевантні результати. Потрiбно тодi створити ще один MCP-iнструмент, який буде використовуватися для семантичного пошуку за допомогою векторного пошуку.

**Як будете тестувати? Які ключові кейси перевірите?**

Для MVP я б використав комбінацію кількох підходів:

1. **Golden Dataset.** Створити набір тестових запитів із заздалегідь відомими правильними відповідями. Він стане еталоном для перевірки поведінки агента.
2. **Детерміновані перевірки.** Переконатися, що агент викликає правильний MCP-інструмент із правильними параметрами та повертає коректну структуру відповіді.
3. **LLM-as-a-Judge.** Для оцінки природності відповідей, релевантності, достовірності та змістової відповідності можна використовувати сильнішу LLM як автоматичного оцінювача.
4. **Автоматизоване тестування.** Використати такі інструменти, як Promptfoo або LangSmith, для запуску тестових сценаріїв, оцінювання відповідей і трасування викликів інструментів.
5. **Ручне тестування edge cases.** Перевірити спроби prompt injection, питання поза предметною областю магазину, некоректні або неіснуючі ID товарів, порожні результати пошуку, а також ситуації, коли Product API недоступний або повертає помилку (наприклад, при падiннi сервера/iнфраструктури).
